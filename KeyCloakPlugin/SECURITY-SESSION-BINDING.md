# ZeroOTP Keycloak v1.1.0 — Cryptographic Session Binding

## Purpose

This document describes the security change introduced in ZeroOTP Keycloak plugin v1.1.0. It focuses narrowly on the mechanism that binds the RFC 6238 TOTP component to a specific Keycloak authentication session.

The repository-wide security model and NIST/Microsoft mapping are documented in [`../SECURITY-ARCHITECTURE.md`](../SECURITY-ARCHITECTURE.md).

---

## 1. Problem addressed

Protecting a TOTP secret with WebAuthn PRF is valuable but does not, on its own, change the semantics of a conventional TOTP output. If the verifier accepts only a six-digit code, a valid code can in principle be captured and relayed during its validity window.

NIST SP 800-63B-4 defines phishing resistance as a property of the **authentication protocol**, not merely of secret storage. The protocol must prevent an impostor verifier from obtaining authentication secrets or valid authenticator outputs that can be used against the legitimate verifier without depending on the claimant to detect the phishing site.

For this reason, v1.1.0 makes the RFC 6238 value necessary but **not sufficient**.

---

## 2. Server challenge

For each Hardware TOTP login, `HardwareTotpAuthenticator` creates 32 random bytes using `SecureRandom` and serializes the value as unpadded Base64URL.

```text
challenge = Base64URL(SecureRandom(32 bytes))
```

The value is stored as an authentication-session note:

```text
HARDWARE_TOTP_LOGIN_CHALLENGE
```

and is sent to the corresponding login page as `serverChallenge`.

The challenge is scoped to the current Keycloak `AuthenticationSession`; it is not a static realm value and it is not generated by JavaScript.

---

## 3. Challenge use in WebAuthn + PRF

The browser decodes the Keycloak challenge and supplies it to the WebAuthn `navigator.credentials.get()` call while requesting PRF evaluation:

```text
Keycloak serverChallenge
        |
        v
navigator.credentials.get({
    challenge: serverChallenge,
    userVerification: "required",
    extensions: {
        prf: { eval: { first: prfSalt } }
    }
})
```

This combines two roles in one ceremony:

- WebAuthn uses the challenge as freshness input for the RP-bound credential operation.
- The PRF extension evaluates the credential-associated pseudo-random function only through that WebAuthn credential path.

ZeroOTP then applies HKDF-SHA-256 to the PRF output and decrypts the AES-GCM-protected local TOTP vault.

---

## 4. Session proof construction

After recovering the TOTP secret `K`, the browser computes the normal RFC 6238 code. It does **not** alter the TOTP formula.

The browser then computes:

```text
M = "zerotp-session-v1\0" || challenge || "\0" || totpCode
sessionProof = HMAC-SHA-256(K, M)
```

The components have distinct purposes:

| Component | Purpose |
|---|---|
| `K` | Shared authentication key already required for RFC 6238 verification |
| `zerotp-session-v1\0` | Protocol/domain-separation label; prevents the MAC input from being ambiguous with unrelated uses of the same key |
| `challenge` | Fresh verifier-generated 256-bit authentication-session value |
| `\0` | Explicit field separator |
| `totpCode` | Binds the proof to the exact RFC 6238 value submitted in this transaction |
| HMAC-SHA-256 | Provides message authentication of the session-bound data under `K` |

The returned HTTP form therefore carries both:

```text
totpCode=<RFC6238 value>
sessionProof=<Base64URL HMAC-SHA-256 value>
```

---

## 5. Server verification

`HardwareTotpCredentialProvider.isValidBound()` performs the following logic:

```text
1. Locate the user's hardware-prf-totp credential.
2. Validate the submitted TOTP for the accepted time window.
3. Decode the credential's TOTP secret K.
4. Recompute HMAC-SHA-256(K, label || challenge || separator || TOTP).
5. Decode the submitted Base64URL proof.
6. Compare proof values with MessageDigest.isEqual().
7. Return success only if both TOTP and proof are valid.
```

After the attempt, `HardwareTotpAuthenticator` removes the challenge note:

```text
removeAuthNote("HARDWARE_TOTP_LOGIN_CHALLENGE")
```

The challenge is therefore single-use at the application protocol layer.

## 6. Security properties

### 6.1 TOTP capture no longer suffices

A phisher that learns only:

```text
123456
```

cannot complete authentication because Keycloak also requires a valid 256-bit HMAC proof.

### 6.2 Cross-session relay fails

Assume an attacker captures from session A:

```text
TOTP_A
proof_A = HMAC(K, challenge_A || TOTP_A)
```

A second authentication session B contains a distinct verifier-generated challenge:

```text
challenge_B != challenge_A
```

Keycloak computes:

```text
expected_B = HMAC(K, challenge_B || TOTP_submitted)
```

and `proof_A` does not match `expected_B` except with negligible cryptographic probability, assuming the HMAC key remains secret and HMAC-SHA-256 retains its expected security properties.

### 6.3 Replay resistance

The design combines several freshness controls:

- RFC 6238 time-step validity;
- a statistically unique 256-bit verifier challenge;
- challenge state stored in the authentication session;
- challenge deletion after the verification attempt.

The challenge is the stronger anti-replay element because the same TOTP value can be valid for multiple requests within its time window, while the proof changes with the session challenge.

### 6.4 Verifier-name binding

The PRF evaluation is reached through WebAuthn. WebAuthn credentials are RP-scoped and NIST explicitly cites WebAuthn/FIDO2 as an example of verifier-name binding. An impostor origin cannot simply request the genuine RP's credential as though it were the genuine verifier.

### 6.5 Separation between PRF and session proof

These mechanisms solve different problems:

- **PRF + HKDF + AES-GCM:** protects the browser-side copy of `K` and requires use of the WebAuthn credential before the application can recover it.
- **sessionProof:** prevents the recovered TOTP value from being accepted outside the Keycloak authentication session for which it was produced.

Neither should be described as a substitute for the other.

---

## 7. NIST interpretation

NIST SP 800-63B-4 states that phishing resistance requires a cryptographic authentication protocol and recognizes verifier-name binding and channel binding. It excludes manually entered OTP authenticators because manual transfer does not bind the authenticator output to the specific session.

The v1.1.0 ZeroOTP Keycloak exchange is intentionally different from that excluded pattern:

- the user does not manually transfer the accepted cryptographic proof;
- the verifier contributes a fresh challenge;
- the response is a MAC over that challenge and the TOTP;
- WebAuthn supplies RP/verifier binding to the operation that releases the secret required to create the response.

The strongest defensible description is therefore:

> **ZeroOTP Keycloak v1.1.0 is a session-bound cryptographic authentication protocol that retains RFC 6238 TOTP as an internal compatibility component. Its design is intended to satisfy the NIST phishing-resistance property through WebAuthn verifier-name binding and a verifier-generated challenge authenticated by HMAC-SHA-256.**

This is a protocol analysis, not a statement of NIST certification, FIPS validation, or AAL3 conformance.

---

## 8. Explicit limitations

The design does not protect against every endpoint compromise. In particular:

- arbitrary script execution in the legitimate Keycloak origin can operate with the privileges of that origin;
- compromise of the Keycloak credential database or process that reveals the TOTP secret exposes the symmetric authentication key;
- the verifier stores a symmetric secret, unlike a pure WebAuthn verifier that can store only a public key;
- this session proof is application-layer binding, not TLS channel binding;
- complete WebAuthn attestation trust validation is outside the current implementation;
- AAL3 is not claimed.
