# ZeroOTP — Keycloak Hardware TOTP Integration

## WebAuthn PRF-protected, session-bound authentication for Keycloak

This directory is the Keycloak integration layer of the ZeroOTP repository. It is not a separate project: it derives the standalone ZeroOTP PRF-protection model and adds the verifier-side state and cryptographic session binding required for a stronger authentication protocol.

The implementation has been compiled, deployed, and functionally tested with Keycloak in Docker on macOS.

> **Security-critical change in v1.1.0:** the six-digit RFC 6238 TOTP is no longer sufficient to authenticate. Every login also requires a fresh HMAC-SHA-256 proof bound to a 256-bit challenge generated and stored by Keycloak for the current `AuthenticationSession`.

> **Security-critical change in v1.2.0:** every successful login now requires server-side verification of the WebAuthn assertion generated by the same `navigator.credentials.get()` ceremony that evaluates PRF. Keycloak verifies credential ID, challenge, origin, RP ID hash, UP/UV flags, and the authenticator signature before evaluating TOTP and `sessionProof`. Existing v1.1 credentials do not contain the WebAuthn public key and must be re-enrolled.

---

## 1. Design objective

ZeroOTP starts from a compatibility requirement: keep an RFC 6238 TOTP secret and code so that the verifier can retain TOTP semantics, while avoiding a permanently recoverable plaintext secret on the browser endpoint.

The plugin adds two security layers around that TOTP component:

1. **WebAuthn PRF protection of the browser-side TOTP secret.** The local encryption key is derived only after a successful WebAuthn operation for the enrolled credential with user verification required.
2. **Cryptographic authentication-session binding.** Keycloak generates a fresh challenge for every login and accepts the TOTP only when accompanied by a valid HMAC proof for that same challenge and code.

Therefore the correct model is not “a phishing-resistant six-digit OTP.” The six-digit TOTP remains a compatibility component inside a broader **verifier-bound and session-bound cryptographic authentication protocol**.

## 8. Enrollment protocol

Enrollment creates the server-side RFC 6238 secret and a browser-side encrypted copy. The local copy is sealed with a key that can be reconstructed only by evaluating the WebAuthn PRF for the enrolled credential.

```text
Keycloak creates TOTP secret
        |
        v
Browser creates WebAuthn credential
userVerification = required
PRF extension requested
        |
        v
Browser evaluates credential PRF
        |
        v
PRF output (32 bytes)
        |
        v
HKDF-SHA-256
        |
        v
AES-GCM key
        |
        v
Encrypt { TOTP secret, issuer }
        |
        v
Store only ciphertext + IV + PRF/HKDF inputs
in origin-scoped localStorage
        |
        v
Register Keycloak credential metadata
```

### 8.1 Role of WebAuthn PRF

The W3C WebAuthn Level 3 PRF extension exposes a credential-associated pseudo-random function whose outputs are 32 bytes. The function is associated with the WebAuthn credential; the application supplies an input (`prfSalt`) and receives the PRF output through a successful WebAuthn ceremony.

ZeroOTP does **not** persist that output. Instead:

```text
PRF(credential, prfSalt)
        |
        v
HKDF-SHA-256(prfOutput, hkdfSalt, info="zerotp-hardware-totp-aes-key")
        |
        v
AES-256-GCM key
```

The derived AES key encrypts the local TOTP material. At a later login, the same credential and the same PRF input reproduce the input keying material, allowing the browser to derive the same AES key and decrypt the vault.

This separates **secret-at-rest protection** from TOTP itself. The TOTP secret is not protected by a reusable typed master password in the PRF path; access depends on successful use of the enrolled WebAuthn credential and its user-verification policy.

The plugin has no weaker non-PRF fallback. If PRF is unavailable, enrollment fails.

### 8.2 Stored local record

The browser stores values equivalent to:

```text
credentialId
prfSalt
hkdfSalt
AES-GCM IV
AES-GCM ciphertext
```

The plaintext TOTP secret and the derived AES key are not intentionally persisted by the plugin.

## 9. Authentication protocol — v1.1.0 session binding

### 9.1 Why the original PRF-only design was insufficient

PRF strongly protects access to the local TOTP secret and WebAuthn constrains the credential ceremony to the RP/origin. However, if the final server request contains only a normal six-digit TOTP, that value remains an OTP authenticator output. If an attacker obtains it while valid, it has no intrinsic cryptographic reference to the Keycloak authentication session that caused it to be generated.

NIST SP 800-63B-4 defines phishing resistance in terms of preventing disclosure of authentication secrets and **valid authenticator outputs** to an impostor verifier. It specifically explains that manually transferred OTP authenticators are not phishing-resistant because their output is not bound to the session being authenticated.

Version 1.1.0 changes the server protocol so that the TOTP is not accepted independently.

### 9.2 Verifier-generated challenge

When `HardwareTotpAuthenticator.authenticate()` creates the login form, it generates 32 random bytes with Java `SecureRandom`, Base64URL-encodes them, and stores the value in the current Keycloak authentication session:

```text
AuthenticationSession note:
HARDWARE_TOTP_LOGIN_CHALLENGE = <256-bit random challenge>
```

The same value is rendered into the login page as `serverChallenge`.

### 9.3 WebAuthn ceremony uses the verifier challenge

The browser decodes the server challenge and supplies it to `navigator.credentials.get()`:

```javascript
publicKey: {
    challenge: serverChallenge,
    allowCredentials: [...],
    userVerification: "required",
    extensions: { prf: { eval: { first: prfSalt } } }
}
```

This is significant for two independent reasons:

- the WebAuthn assertion ceremony itself is fresh and tied to the challenge generated by Keycloak;
- PRF evaluation occurs inside that RP-bound WebAuthn operation.

The current plugin does not submit and independently verify the complete WebAuthn assertion signature as the final Keycloak credential. WebAuthn is being used to gate/evaluate PRF and provide RP-bound credential use. The final ZeroOTP verifier check is the HMAC session proof described below.

### 9.4 TOTP generation remains RFC 6238 compatible

After PRF output reconstruction and AES-GCM decryption, the browser computes the normal time-based OTP:

```text
T = floor(currentUnixTime / period)
TOTP = HOTP(K, T)
```

The default implementation uses the standard six-digit/30-second pattern unless credential parameters specify otherwise.

Nothing is inserted into the RFC 6238 calculation that would make the value incompatible with a conventional TOTP verifier.

### 9.5 Session proof

The browser then computes a second authenticator output using the TOTP shared secret as the HMAC key:

```text
sessionProof = HMAC-SHA-256(
    K,
    "zerotp-session-v1\0" || challenge || "\0" || TOTP
)
```

where:

- `K` is the decoded TOTP secret;
- `zerotp-session-v1\0` is a protocol/domain-separation label;
- `challenge` is the Base64URL Keycloak challenge stored in the `AuthenticationSession`;
- `TOTP` is the exact RFC 6238 code being submitted.

The browser Base64URL-encodes the 256-bit MAC and submits:

```text
totpCode
sessionProof
```

### 9.6 Server verification

`HardwareTotpCredentialProvider.isValidBound()` performs both checks:

1. validate the RFC 6238 code for the current time window;
2. recompute HMAC-SHA-256 using the verifier-side copy of the same TOTP secret, the server-side session challenge, and the submitted code;
3. compare the expected and submitted MAC values with `MessageDigest.isEqual()`;
4. accept only if both checks succeed.

The authenticator removes the challenge from the `AuthenticationSession` after the verification attempt, whether successful or unsuccessful.

### 9.7 Security effect

The accepted authenticator output is therefore not merely:

```text
123456
```

It is effectively:

```text
123456 + MAC_K(protocol-label || challenge_A || 123456)
```

A different Keycloak authentication session receives `challenge_B`. Replaying the captured pair from session A produces a MAC mismatch because:

```text
challenge_A != challenge_B
```

This is the explicit cryptographic session binding that the original PRF-only design lacked.

## 10. NIST-oriented classification

The detailed assessment is in the repository-level [`../SECURITY-ARCHITECTURE.md`](../SECURITY-ARCHITECTURE.md). The concise position is:

- **Do not describe the v1.1.0 plugin as a conventional Multi-Factor OTP authenticator.** RFC 6238 is retained internally, but the verifier requires a second cryptographic response bound to its challenge.
- The v1.1.0 authentication exchange is best analyzed as a **multi-factor cryptographic challenge-response protocol using a symmetric authentication key**, activated through a WebAuthn credential with user verification, with verifier-name binding contributed by WebAuthn and freshness/session binding contributed by the Keycloak challenge and HMAC proof.
- The design is intended to satisfy the NIST SP 800-63B-4 phishing-resistance property: a phishing verifier should not obtain a reusable valid authenticator output for the genuine verifier merely by collecting a six-digit OTP.
- This is an architectural classification, not a NIST certification or FIPS validation.
- **Do not claim AAL3.** AAL3 adds requirements that this design does not establish, including public-key cryptography for the AAL3 cryptographic authenticator, non-exportable authentication keys, and applicable validation requirements.

## 11. Microsoft Entra terminology

Microsoft Entra `Authentication strengths` are an allow-list of Microsoft-recognized authentication methods/combinations. A custom Keycloak SPI does not automatically become an Entra `Phishing-resistant MFA strength` method because its protocol properties are similar to phishing-resistant methods.

If Keycloak is used as a federated IdP for Entra, how the authentication is represented to Entra and what Conditional Access can recognize is a separate integration question. Microsoft currently lists FIDO2/passkeys, Windows Hello/platform credentials, and multifactor certificate-based authentication among the built-in phishing-resistant methods. Generic federated multifactor appears in the baseline MFA strength rather than the built-in phishing-resistant strength.

See [`../COMPLIANCE.md`](../COMPLIANCE.md) for the distinction between **protocol security classification** and **Microsoft policy-engine recognition**.

## 12. Security boundaries and limitations

### Shared verifier secret

Keycloak stores the RFC 6238 secret because it validates both TOTP and the symmetric HMAC session proof. Server compromise that exposes this key can enable impersonation. This differs from a pure public-key WebAuthn verifier, which stores only public keys.

### Endpoint compromise

PRF, AES-GCM, and session binding protect against important phishing/relay classes; they do not make a compromised browser trustworthy. Malicious code executing in the genuine RP origin at the right time may access plaintext application data after decryption or alter requests.

### Attestation

Enrollment asks for WebAuthn attestation and records metadata such as AAGUID/BE/BS information, but the current implementation does not perform a complete trust-policy validation against FIDO Metadata Service roots and metadata statements.

### Local browser state

The encrypted vault is stored in origin-scoped `localStorage`. A passkey/PRF credential alone is not sufficient if the corresponding encrypted vault record is absent. Consequently, registering or having access to a related passkey on another device does not automatically transfer the encrypted TOTP material required by this plugin.

### TLS

Production deployments require HTTPS and normal reverse-proxy/header hardening appropriate for Keycloak. The included `localhost` HTTP configuration is for development only.
