NIST & Microsoft Authentication Framework Mapping

Companion page to the summary on index.html. Source markdown: COMPLIANCE.md. Last checked against sources: September 2026.

This page maps each ZeroOTP storage method to current NIST and Microsoft authentication guidance, and links to the primary sources.

Frameworks used

NIST SP 800-63B-4 — Digital Identity Guidelines: Authentication and Authenticator Management. Final revision published July 2025, superseding SP 800-63B-3. Defines three Authenticator Assurance Levels (AAL1/AAL2/AAL3) and, new in this revision, explicit guidance for syncable authenticators (passkeys stored in a cloud-synced vault such as Chrome/Google Password Manager, iCloud Keychain, etc.), integrating NIST's April 2024 interim passkey guidance as normative text.

  • Overview: pages.nist.gov/800-63-4
  • SP 800-63B-4 full text: pages.nist.gov/800-63-4/sp800-63b.html
  • Publication record: csrc.nist.gov/pubs/sp/800/63/b/4/final

Microsoft Entra ID — Conditional Access authentication strengths. Three built-in tiers — MFA strength, Passwordless MFA strength, and Phishing-resistant MFA strength — each accepting a specific, progressively narrower set of authentication method combinations.

  • Overview: learn.microsoft.com … concept-authentication-strengths
  • Phishing-resistant deployment guide: learn.microsoft.com … phishing-resistant-passwordless-authentication

Biometric / passkey (biometry.html, full.html) WebAuthn public-key credential (passkey) with platform user verification (Touch ID / Windows Hello / Android biometrics), PRF-derived AES-GCM key AAL2 when the passkey is a syncable credential held in Chrome/Google Password Manager (this project's case), per the syncable-authenticator provisions in 800-63B-4 Appendix B. Genuinely phishing-resistant — the credential is cryptographically bound to this origin. Would need a non-syncable, device-bound passkey to claim AAL3, which is not what Chrome Password Manager stores. Qualifies for all three tiers, including Phishing-resistant MFA strength (the "FIDO2 security key / Windows Hello for Business or platform credential" family)
Biometric fallback "gate" mode (js/biometric.js) Non-extractable AES-GCM key in IndexedDB, WebAuthn assertion required by application logic only Does not meet the AAL2 phishing-resistance bar in the same sense — the biometric check is enforced by this page's code, not by a cryptographic binding between the credential and the key. Would not qualify as "phishing-resistant" under a strict reading, since the binding is not cryptographic

Practical takeaway: if you need to describe ZeroOTP's strongest configuration in security or compliance language — the Biometric method, in its primary PRF mode, is the only one of the four storage backends that is phishing-resistant and maps to NIST AAL2 / Microsoft's Phishing-resistant MFA strength. The three TOTP-based backends (Cookie, LocalStorage, Chrome Password Manager storing a shared secret) are all the same underlying authenticator type — a software OATH token — and all land at the same, lower tier: NIST AAL2 without phishing resistance, Microsoft's baseline MFA strength only.

This is a factual mapping, not a security audit. It describes how the mechanisms this project uses are categorized by these two frameworks — it does not certify ZeroOTP against either one, and neither framework publishes a certification program for hobby/personal-use software like this.
